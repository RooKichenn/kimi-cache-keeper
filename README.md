# kimi-cache-keeper

> 💡 **OpenCode CLI 用户 / AI Agent**：如果你使用的是 OpenCode CLI，请直接查阅 [opencode-plugin/README-opencode-kimi-cache-keeper.md](opencode-plugin/README-opencode-kimi-cache-keeper.md) 获取专属插件安装与配置指南。

一个 Kimi Code CLI 的 Skill:通过定时发送轻量"保活"消息,维持当前会话的服务端 prompt 缓存,让长时间挂着的会话不至于每次开口都全量重算输入,从而降低 token 成本。

## 原理

Kimi Code 的服务端对输入做前缀缓存:两次请求的前缀一致且间隔落在缓存窗口内,输入部分按缓存价计费(近乎免费);否则全量计费。社区观察到的行为是:

- 间隔一段时间后第一句话很贵,后续密集对话很便宜
- 官方缓存窗口已从约 5 分钟提升到 20 分钟以上(随服务端负载波动)

本 Skill 让模型在当前会话创建定时任务,每隔 N 分钟(默认 15)自动注入一条固定的微型消息,模型回复"收到"即结束——用极小的开销把会话前缀一直"捂"在缓存窗口里。

## 两种模式

### 定点循环(默认)

一个 `*/N * * * *` 循环任务,锚定墙钟整点刻(:00/:15/:30/:45)触发。调度器兜底,单次执行失败不影响后续,**健壮性最高**,适合作为默认选择。

### 链式 smart(可选)

一次性任务自我续链:每次触发后自动重建"当前时间 + N 分钟"的下一跳。由于 cron 只在会话空闲时投递,重建时刻天然等于"最后一次活动时间",时机精确、无浪费,且不受 7 天过期限制。

### 模式对比

| 维度 | 定点循环(默认) | 链式 smart |
| --- | --- | --- |
| 触发基准 | 墙钟整点刻,与活动无关 | 相对计时:最后一次活动 + N 分钟 |
| 任务结束后 | 立即补发一次(浪费)+ 下个整点再发 | 结束后重建,下一跳正好 +N 分钟 |
| 空闲期行为 | 每 N 分钟一跳,稳定 | 每 N 分钟一跳,稳定 |
| 每次触发成本 | 极低:回"收到"两个字 | 低:多一次 date + CronCreate 调用(约多 100+ tokens) |
| 浪费来源 | 任务结束时的多余补发(见下文) | 几乎为零 |
| 健壮性 | 高:调度器兜底,单次失败不影响后续 | 低:任一跳重建失败即**静默断链**,无告警 |
| 7 天过期 | 有,需 `refresh` 续期 | 无,链条自我延续 |
| 实现复杂度 | 低:一次创建,持续生效 | 中:每跳需正确计算 cron 字段(跨时/跨天/跨月) |

**结论**:日常用定点循环——浪费可量化、有上限、极便宜,"不会死"是它最大的优点。链式适合长会话、长任务极频繁、且愿意偶尔 `status` 抽查的场景。两者随时可用 `off` 后重新 `on` 切换。

## 定点循环什么时候会浪费

浪费发生在**长任务结束的瞬间**,举例:

```
10:05  开启保活(定点循环,15 分钟)
10:10  你发出一个复杂请求,任务开始执行
10:15  整点触发到点 → 你正忙,压住不发
10:30  整点触发到点 → 仍在执行,继续压住
10:30  任务结束 → 堆积的触发合并成一次,立刻补发
       ↑ 这次就是浪费:任务自己的最后一次请求刚刷新过缓存,
         缓存窗口从 10:30 才起算,这一跳纯属多余
10:45  下一整点触发(这次是必要的,距上次有效活动 15 分钟)
```

规律:**每段忙碌期结束都会白送一跳**。浪费频率与你的长任务个数成正比;单次浪费的量 = 一次缓存全命中的输入 + 两个字输出,约等于"扣 0.01% 月额度"那一档。一天 6 个长任务,浪费约 0.06%——这是为"调度器兜底、永不静默失效"付的保险费。链式模式没有这个浪费,但要用每跳略高的成本和断链风险来换。**我目前一直用的还是定点循环，每次任务结束后0.01%月额度的浪费是可以忽略的**

## 会污染上下文吗

会有占用,但量级极小,可以忽略:

- **占用量**:每次心跳在上下文中增加约 35 tokens(一条固定短消息 + "收到"两个字)。按 15 分钟间隔挂一整天 ≈ 3k tokens,约占 256k 上下文窗口的 1.2%——随便读一个文件的开销都比一天的心跳总量大
- **语义干扰**:心跳内容单调重复,模型对它们的注意力权重很低,不会盖过真正的任务上下文
- **compact 时自清**:上下文接近上限触发压缩时,这些无信息量的消息会在摘要阶段被最先丢弃,不占用压缩后的空间
- **不破坏缓存**:心跳是追加在上下文末尾的,而前缀缓存本来就允许末尾增长——下次请求命中的是"上一次请求为止的全部前缀",维持缓存和追加消息不矛盾

结论:一天约 3k tokens 的窗口占用,换来每次开口不用全量重算几万甚至十几万 tokens 的输入,这笔账是划算的。觉得碍眼时 `/compact` 一次即可清干净。

## 用法 (Kimi Code CLI)

在任意会话中:

```
/cache-keeper on             # 定点循环,每 15 分钟
/cache-keeper on 12          # 定点循环,自定义间隔(分钟)
/cache-keeper on smart       # 链式模式,每 15 分钟
/cache-keeper on 12 smart    # 链式模式,自定义间隔
/cache-keeper status         # 查看保活任务状态(可省略为 /cache-keeper)
/cache-keeper refresh        # 定点循环 7 天过期后续期重建(链式不需要)
/cache-keeper off            # 关闭保活
```

## 必须知道的限制

- **绑定会话**:定时任务只活在创建它的那个会话里。新开会话需重新 `on`;CLI 关闭期间不触发,`--resume` 恢复同一会话后自动继续。
- **7 天过期**(仅定点循环):循环任务在创建 7 天后被系统自动过期,执行一次 `/cache-keeper refresh` 即可重置周期。链式模式无此问题。
- **静默断链**(仅链式):某一跳重建失败则链条中断且无告警,建议偶尔 `status` 抽查。
- **只在空闲时触发**:正在跑长任务时不会打断,顺延到任务结束后的空闲点合并触发。
- **效果无法从客户端保证**:缓存窗口是服务端行为、随负载波动;命中率没有客户端标志位,只能通过用量明细(每次请求的扣费幅度)间接观察。
- **保活本身有微小开销**:每次触发是一次极短的模型请求,正常间隔下远低于缓存过期后全量重算的成本。

## 搭配建议:主模型规划 + 便宜模型搬砖

保活解决"主会话输入贵"的问题,子代理解决"干活贵"的问题,两者互补:

- 主会话用强模型(如 K3)做规划、审阅、对话——吃缓存
- 派子代理写代码时用便宜模型:`Agent` 工具的 `model` 参数选 `deepseek/deepseek-v4-flash`,或在 CLI 里用 `/secondary-model` 设置子代理默认模型

注意:**不要用子代理执行本 Skill**。缓存绑定主会话前缀,子代理是独立上下文,派它发心跳或建任务都无效(Skill 内部已禁止)。
